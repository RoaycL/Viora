# 14 · TV 性能优化与测量

## 第一批：首页与图片（v0.15.2）

- TV 首页保留轻量的行占位，只有接近视口或遥控器进入该行时才订阅推荐数据、构建海报。远离视口且没有焦点的行释放组件，重新进入恢复每行焦点和横向位置。空结果行隐藏并从导航中移除；窗口变化和空行折叠会重新检查可见区域。
- 首页背景与推荐行的 Riverpod 更新分开，深处推荐数据不会阻塞首屏。继续观看和最近入库的海报也按视口构建。Windows 保持现有完整推荐布局。
- TV 横排预构建范围由 1600 设计像素缩小到约一张卡片。解码图片缓存限制为 64 MiB / 160 项，收到系统内存压力通知时释放未使用缓存。它不代表整个进程的内存上限，活跃图片、视频解码器和 GPU 纹理需另外测量。
- 图片复用 HTTP 客户端与连接，TV 最多同时下载 4 张，桌面最多 6 张（单个主机最多 4 条连接）。当前背景优先于普通海报，Hero 下一张预热优先级最低，进入视口后可以提升队列优先级。相同 URL 的不同鉴权头不会共用缓存。
- 原有 1920 宽 TV 解码上限和 Hero 完整详情缓存保留。

## 如何在电视测量

正式 Release 默认不注册帧回调，也不启动统计计时器。开发时使用 **Profile** 构建并显式打开：

```sh
flutter build apk --profile --dart-define=VIORA_FRAME_STATS=true
```

需要构建默认 TMDB Token 时沿用项目既有的 `VIORA_TMDB_TOKEN` 构建配置。

新版本 main 的 CI 同时生成 `android-tv-performance` Artifact，包含优化版 `android-profile.apk` 和对照版 `android-profile-baseline.apk`；从对应 Actions 运行页下载。它们单独保存，不进入 Release 自动更新资产。正式版和测量版使用相同应用 ID，可覆盖安装；完成测量后安装正式 APK。

对照版在相同源码和帧统计下，通过额外的 `--dart-define=VIORA_TV_PERF_BASELINE=true` 关闭本批的 TV 行懒加载、横排预构建缩小、图片连接复用 / 并发限制及图片缓存预算。既有 TV 优化和鉴权缓存隔离仍保留，所以它是本批优化的对照模式，并非旧版本的完整复刻。这个开关只对非 Release 的 TV 构建有效。

安装测量 APK 后，重复下面流程，再在「设置 → 导出日志」导出：

1. 冷启动首页，等待首屏稳定，连续按下 / 上浏览全部推荐行，再快速横向移动海报。
2. 重启应用重复相同操作，区分冷缓存和热缓存。固定服务器、网络、TMDB 配置和遥控操作路线。
3. 打开同一视频，记录从点击播放到出画面的时间；播放、暂停、拖动，再返回首页。
4. 日志中筛选 `[perf]`，用 `mode=baseline` / `mode=optimized` 区分构建。先安装对照包测量并导出日志，再安装优化包重复；两者保持相同图片缓存状态。不要使用 Debug 构建作性能基准。

冷缓存比较时，每个包都先在设置中清除图片缓存并重启；热缓存比较时，每个包都先完整浏览一次、重启后再记录，避免第二个包直接受益于第一个包下载好的图片。

每秒有实际 Flutter 帧时记录一条汇总：场景 `home` / `player` / `page`、观察到的帧数、UI 和 Raster 的 P95 / 最大耗时、总延迟 P95、超预算帧数、图片缓存字节数及下载队列。预算由屏幕刷新率决定，60 Hz 约 16.67 ms；慢帧表示 UI 或 Raster 超过预算，不等于视频解码掉帧数。无 Flutter 帧时不输出；每窗口最多保留 1024 个耗时样本，同时完整累计帧数与最大值。应用进入后台暂停汇总计时器。

帧日志直接进入既有的有界日志缓冲区，不逐帧写文件或控制台，不记录作品 ID、地址和凭据。当前日志没有进程 PSS、GC、视频掉帧或自动首帧计时；这些指标需要后续原生采样或 Android 工具补充。

当前测试验证按需请求、屏幕外组件释放、遥控器进入未构建行、行记忆与空行跳过、HTTP 连接复用、鉴权隔离、并发限制、优先级、失败释放槽位和帧统计。实际 TV 的帧耗时与内存收益仍需真机对比，不能从单元测试推导。

本地检查：Dart 3.13.5 与 Flutter 3.47.7 框架源码静态检查通过；Flutter 3.44 兼容副本全量 178 项通过、12 项在线测试跳过，另有对照模式测试通过。兼容副本使用适配其 SDK 的依赖约束，正式项目锁文件未改；完整正式工具链与平台构建由 CI 验证。
